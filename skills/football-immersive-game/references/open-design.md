# 从体验出发，允许新形式

## 先听构想，不先分类型

先请用户讲一个想象中的瞬间：人在什么地方，与谁互动，想做什么，希望世界如何回应。用户也可以从画面、规则、情绪、操作、一次真实经历或一项技术出发，不需要先写完整设定。

把已听到的意图记下来，区分不可替代的目标与暂定的形式。例如“朋友之间产生信任与误会”是目标，“聊天窗口”只是一种实现方式。不要把故事、分支、生涯三类当作必须三选一的入口。

当用户需要灵感，提供少量差异真实的提案，让其自由重组或推翻。比较“玩家实际做什么、得到什么体验、制作代价是什么”，而不只换球星或画风。用户不想被选项限制时直接用自由问答。

## 可组合的设计维度

以下只是帮助发现差异的维度，不是要全部填写的矩阵：

- 行动：观察、控制、判断、表达、协作、竞争、制作、探索，或用户自己的动作。
- 关系：独自体验、同机轮流、同时在线、异步互动、AI/真人角色混合。
- 时间：实时、回合、可暂停、持续世界、现场活动的时间节奏。
- 空间：一张界面、一块球场、虚构世界、真实地点、实体道具与数字界面组合。
- 驱动：叙事、身体技巧、战术判断、资源关系、社交互动、发现与谜题。
- 结果：胜负、改变世界、完成仪式、共同创造、持续陪伴；无需固定终局。

围绕最关键的维度提出下一轮问题。足球可以通过规则、角色关系、文化、空间或情感进入体验，不必都表现成进球和赛季数值。

## 没有现成参考时怎么办

1. 用一小段“玩家经历”描述核心机制，确定输入、规则/他人回应和可感知反馈。
2. 找出最可能不成立的假设：操作是否有趣、谜题是否可解、协作是否必要、画面能否传达空间等。
3. 选择最小验证形式：纸面走查、交互灰盒、单次操作原型、两个客户端的协作样片等。先验证这个假设，无需补齐不相关的章节和结局。
4. 用试玩反馈更新形式。如果机制不成立，改机制而不是堆文案或素材。
5. 原型有效后再确定适合的引擎、状态模型、资源和完整范围。已有项目则优先在既有结构中验证。

在现有参考中只取有用部分。需要陌生引擎、平台能力或 API 时查实际官方文档，明确工具与权限边界。没有相应运行能力时完成可做的验证，清楚指出阻塞，不能用网页壳替代用户要的原生或空间体验后声称完工。

## 条件性技术关注点

| 如果作品涉及 | 需要弄清的关键问题 | 样片证据 |
| --- | --- | --- |
| 实时动作或战术 | 输入映射、延迟、时间步长、失败与重试 | 玩家能完成一次操作并感知反馈 |
| 真人多人 | 每人一机或共用设备、同地或分头、同步/异步、谁决定共享状态、角色权限与公开/私有信息、加入退出和断线重连 | 独立客户端真实交换状态、私有线索不泄漏给其他角色、重连后进度一致；模拟玩家需标注 |
| 解谜或探索 | 线索依赖、信息可得、卡关提示、替代解法 | 不知道答案的人能沿线索推进 |
| 真实地点或实体道具 | 现场可达性、位置权限、离线/无法到场替代、如何验证行动 | 桌面模拟与现场测试分开记录 |
| 持续世界或开放经营 | 状态持久性、时间推进、恢复与扩展成本 | 退出再进入后世界状态合理延续 |
| AI 角色或动态内容 | 可控角色设定、状态一致、服务成本、响应失败兜底 | 动态回应与真实游戏状态一致且可继续游玩 |

只读当前作品有关的行。这张表也可扩展，未列出的机制不代表不支持。
